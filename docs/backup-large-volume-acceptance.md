## Workload and reproducibility

`TestActualLargeVolumeBackupRestore` in `internal/library/backup_large_volume_test.go` is opt-in using `IMMICH_LARGE_BACKUP=1` and `IMMICH_LARGE_TEMP` for disposable storage. The Windows workflow is `.github/workflows/backup-large-volume.yml`. Ordinary tests compile and skip it; local compilation and vet passed.

The preflight requires 18 GiB available. Production `PutWithPath` writes two real synthetic originals, exact 4 GiB and 1 MiB, with deterministic AES-CTR bytes that are poorly compressible. These are unsupported binary fixtures, not natural media or AI workloads. Public constant keys only generate fixture bytes. The test does not allocate the complete payload/archive in memory or rely on sparse files.

A first staged backup is cancelled through its context after at least 64 MiB of actual copy progress. Both the partial archive and catalog snapshot staging must disappear. A complete retry must report exact completed byte/file progress and create an archive larger than 4 GiB. The ZIP reader must report the 4 GiB original and a compressed size crossing the legacy 32-bit field limit. Production VerifyBackup then reads every archived original back and checks its checksum.

The archive is moved outside the original state, that state is renamed offline, and default-budget RestoreWithLimits restores to a separate nonexistent destination. Both restored originals and the offline source originals are streamed and hashed in full, compared with independently regenerated deterministic bytes, expected sizes and import IDs. Catalog names, sizes and source aliases plus a synthetic required secret must round-trip. No repair reads from the source occur during restoration. All temporary files are cleaned up. Outer operation/test/job limits are 24/28/30 minutes; restore defaults remain unchanged.

## Scope

This is library execution on Windows Server 2022 under the CI account, not installer, LocalService/browser, Windows 10, natural-media endurance, physical-device removal or backup-byte resume. Cancellation is cooperative during actual archive copying; it is not forced service termination or interrupted restoration. Previous smaller installed backup/restart evidence remains separate. This is not complete milestone 5 acceptance.

Security Group 2/3 work, every-frame Full Scan and the known unexplained restore progress-read:32 issue remain outside this work. A successful restore does not establish a fix for that intermittent issue. No user-PC workload or new installer is required for this checkpoint.

# Release 0.1.43 planning: organizing and accessing media

Research date: November 5, 2026 (America/Chicago). Baseline: published 0.1.42 prototype. This is a planning report, not a claim that proposed functionality has shipped.

**The strongest opportunity is to make the library useful for everyday browsing and organization.** Our storage, recovery, analysis, and correction foundations are substantial. The larger user-facing gaps are albums, favorites, useful gallery filters, bulk organization, navigation between photos, and navigation through time. Those deserve attention before adding more sophisticated AI.

The three changes from the earlier discussion are confirmed backlog items: clearer dates, gallery search, and automatic identification of known people. This research identifies **44 additional candidates**, including improvements to partial functionality and ideas best deferred or excluded. The detailed register explains the value, current gap, effort, and recommendation for every candidate.

## 1. Scope and method

I read the referenced **Release 0.1.42 discussion** and compared public product documentation with the released-source snapshot in `work/release-0.1.42/source`. The development folder's older README and roadmap still describe 0.1.39, so they were not used as the shipped-feature inventory. The 0.1.42 snapshot's status and acceptance records identify the published baseline.

The five additional comparison products are **Google Photos, Apple Photos, Adobe Lightroom Classic, digiKam, and ACDSee Photo Studio Home 2026**. They are representative leading products, not an asserted top-five ranking by active users. There is no consistent, audited usage measure spanning cloud services, bundled operating-system applications, and desktop catalog managers. These choices cover consumer retrieval, family collections, professional cataloging, open-source local management, and Windows desktop organization.

Immich and Elements Organizer received the deepest review. For the other five, I concentrated on the organizing, finding, viewing, and retrieving chapters. Only primary documentation supports feature claims below. This is documentation research and code inspection, not hands-on competitive testing. A documented feature's existence does not establish its quality or performance. Product guides are mutable; some describe beta or platform-specific functionality. Those limits are identified where relevant. Older Elements pages were used for the documented workflow, not as proof that every historical dependency or integration remains appropriate.

Development priorities and effort are my assessment. **Small** means a bounded addition using existing records or controls; **Medium** means durable metadata plus UI, indexing, backup, and recovery changes; **Large** means new analysis, substantial indexing or import/export work; **Very large** means an architectural or product-scope expansion. These are relative sizes, not calendar estimates or promises.

## 2. What 0.1.42 already has

| Area | Observed baseline | What that means for planning |
|---|---|---|
| Storage and import | Immutable managed originals, checksum-based deduplication, selected-file/folder import, retained relative source aliases, durable import recovery. | Do not propose basic importing or exact-byte duplicate avoidance as new. Folder browsing and import-session browsing are separate gaps. |
| Gallery | Paged grid; capture-date sorting with import fallback, upload-date sorting, case-insensitive filename sorting; month headings; visible/hidden views. | Basic sorting and grouping already exist. Date-range filters, jump-to-date, reverse order, and richer view choices are extensions. |

Absence statements mean no supported workflow was found in those production models, routes, pages, and project records; they are not an assertion about every experiment in the workspace.

## 3. Confirmed improvements carried forward

| ID | Required behavior | Why it merits development time | Completion evidence |
|---|---|---|---|
| R43-01 | Use **Date taken** or **Date imported**. Put timezone details in information, accurately distinguishing absent from unread data. | Users can understand chronology without interpreting implementation language. Small for wording; broader timezone extraction is separate. | Fixtures with capture date, missing date, embedded offset not currently parsed, and no offset. Correct labels, unchanged originals, no invented timezone. |
| R43-02 | Search within **Photos & videos**, preserving query, result count, clear control, paging, and ordinary gallery cards. Match names, filenames, and tags; only assigned identities count as people. | Makes existing organization useful for the user's central task: finding and viewing pictures. Medium; can reuse authoritative names/tags but needs catalog-wide filtering and paging. | Alice-only, Alice/Bob, filename and tag matches; suggestions excluded; hidden items handled consistently; filtered paging, clear, viewer return, empty results, and large catalog coverage. |
| R43-03 | Automatically assign strong, unambiguous known-person matches after new import/analysis; keep uncertainty in review; distinguish automatic/manual names and preserve corrections. | Removes repetitive confirmation work and makes recognition materially useful over time. Large because incorrect naming has lasting effects. | Independent evaluation of automatic assignment, correction/undo, multiple faces, restart, reanalysis, export and restore. Prevent automatic errors from becoming trusted training references. |

These requirements are now in [the project to-do list](todo.md). A person association belongs to the relevant face; it does not have to be an ordinary custom tag. A photo of Alice and Bob must be found under either assigned identity.

## 6. Five additional tools: findings that add to the comparison

### Google Photos

The computer guide documents manual albums, cover changes, ordering, album text/maps, and live albums that add selected people/pets automatically. Selecting multiple people means either person qualifies; that is an important distinction from an all-people search. These support manual albums first and explicit saved-rule behavior later. Availability varies by country. [Albums](https://support.google.com/photos/answer/6128849?co=GENIE.Platform%3DDesktop&hl=en)

Named face groups can be browsed, combined, and corrected; people/pet search and content/place search reduce dependence on filenames. The key lesson is a person-to-gallery entry point. [Face groups](https://support.google.com/photos/answer/6128838?co=GENIE.Platform%3DDesktop&hl=en), [search](https://support.google.com/photos/answer/15235862)

Archive removes timeline clutter while leaving items searchable and in albums; trash is a different recovery state. Document sorting also groups practical content such as receipts. Automatic stacks are documented for the mobile app, so they are inspiration for a desktop feature, not a claim about the web client. [Archive](https://support.google.com/photos/answer/7362432?hl=en-en), [restore](https://support.google.com/photos/answer/9343482/restore-recently-deleted-or-archived-items?co=GENIE.Platform%3DDesktop&hl=en), [documents](https://support.google.com/photos/answer/14187361?hl=en-MP), [stacks](https://support.google.com/photos/answer/14169846?hl=en-en)

### Apple Photos

Mac Smart Albums combine one or more conditions with any/all semantics and update automatically; the guide warns that these Mac Smart Albums do not appear on iPhone/iPad. Keywords, searchable captions/titles, favorites, and editable date/time/location give users control over machine-generated organization. [Smart Albums](https://support.apple.com/guide/photos/create-smart-albums-pht6d60ca71/mac), [keywords](https://support.apple.com/guide/photos/add-keywords-pht8d0ad5198/mac), [metadata and favorites](https://support.apple.com/en-gb/guide/photos/phta4e5a733f/11.0/mac/26)

People & Pets supports representative photos, favorites, manual ordering, renaming, merging, and reviewing additional matches. Duplicate review offers merging and a recovery destination for removed duplicates. These reinforce identity management and reversible cleanup; pet recognition itself would require separate model work in our app. [People & Pets](https://support.apple.com/guide/photos/find-and-name-people-and-pets-phtad9d981ab/mac), [duplicates](https://support.apple.com/en-ie/guide/photos/pht5a3157c1d/mac)

The current Mac guide also describes natural-language retrieval, including moments in video, with Apple Intelligence requirements. That is a longer-term retrieval direction, not proof that our sampled-video analysis can find every moment. [Search](https://support.apple.com/en-mk/guide/photos/pht64de33e5a/mac)

### Adobe Lightroom Classic

Regular collections, collection sets, and rule-based Smart Collections distinguish selected membership from computed membership. Library filters refine the same grid using text, attributes, and metadata. Flags, stars, color labels, and keyboard assignment support rapid selection work. [Collections](https://helpx.adobe.com/lightroom-classic/desktop/organize-photos-in-lightroom-classic/photo-collections.html), [catalog search](https://helpx.adobe.com/lightroom-classic/desktop/organize-photos-in-lightroom-classic/finding-photos-catalog.html), [ratings and flags](https://helpx.adobe.com/lightroom-classic/desktop/organize-photos-in-lightroom-classic/flag-label-rate-photos.html)

Stacks keep related shots compact. Filter-lock behavior, multiple selection, and batch metadata changes show why navigation state and operation scope deserve explicit rules. Capture-time correction can shift a batch while preserving relative times. [Stacks](https://helpx.adobe.com/lightroom-classic/desktop/organize-photos-in-lightroom-classic/grouping-photos-stacks.html), [browsing and filtering](https://helpx.adobe.com/lightroom-classic/desktop/viewing-photos/browse-compare-photos.html), [metadata actions](https://helpx.adobe.com/lightroom-classic/desktop/organize-photos-in-lightroom-classic/metadata-basics-actions.html)

Video tools include scrubbing, poster-frame choice, and frame capture. Missing-file views explain unavailable originals and support relinking referenced files. Our managed copies reduce that specific linking problem, so we should borrow the clear availability feedback rather than adopt a referenced-file architecture by default. [Video](https://helpx.adobe.com/lightroom-classic/desktop/organize-photos-in-lightroom-classic/video-lightroom.html), [missing files](https://helpx.adobe.com/lightroom-classic/desktop/manage-catalogs-and-files/locate-missing-photos.html)

### digiKam

The manual offers album, tag, rating/pick/color label, date, timeline, search, similarity, map, and people views over the collection. Search can be saved as a live view; hierarchical tags provide vocabulary structure. This is a strong model for multiple routes into one gallery without duplicating media. [Interface](https://docs.digikam.org/en/main_window/interface_layout.html), [search](https://docs.digikam.org/en/left_sidebar/search_view.html), [tags](https://docs.digikam.org/en/left_sidebar/tags_view.html), [labels](https://docs.digikam.org/en/left_sidebar/labels_view.html)

Similarity tools cover duplicate detection, finding a similar image, and searching by sketch. A light table supports comparison. XMP settings can write only sidecars, including organizational fields and face regions, which fits our immutable-original requirement better than embedded writes. [Similarity](https://docs.digikam.org/en/left_sidebar/similarity_view.html), [light table](https://docs.digikam.org/en/light_table.html), [metadata and sidecars](https://docs.digikam.org/en/setup_application/metadata_settings.html)

The current manual also documents local natural-language conversion into structured filters. This is distinct from semantic image-content retrieval: interpreting “photos from last year with four stars” does not itself recognize untagged beaches. Automatic quality/pick-label assignment is another optional workflow. [Query interpretation](https://docs.digikam.org/en/left_sidebar/search_view.html), [quality labels](https://docs.digikam.org/en/left_sidebar/labels_view.html)

### ACDSee Photo Studio Home 2026

The Windows Home 29 guide documents categories, ratings, metadata-derived categories, any/all matching, and saved advanced searches. Advanced Search can operate over the database, chosen folders, or the current view. This adds a useful lesson: always make the current search scope obvious. [Catalog pane](https://help.acdsystems.com/en/acdsee-home-29/Content/1Topics/Manage_mode/Organizing/IDDH_CATALOG_PANE.htm), [Advanced Search](https://help.acdsystems.com/en/acdsee-home-29/Content/1Topics/Manage_mode/Searching/IDDH_SEARCH_PANE.htm)

Face recognition has an explicit automatic-naming option alongside reviewable suggestions; it also supports manual face outlines and face-data imports. We already have manual outlines, so the new value is automatic assignment and controlled interoperability. Imports can overwrite existing face data in ACDSee; our migration design should instead preview conflicts. [Face detection and recognition](https://help.acdsystems.com/en/acdsee-home-29/Content/1Topics/View_mode/WorkingImages_Vmode/Face_Detection.htm)

Image baskets gather files across folders for a task without moving them. Next/previous, full screen, zoom, and keyboard commands make viewing efficient. This supports a temporary selection basket and a better viewer, separate from permanent albums. [Home 2026 manual, image baskets, p. 86](https://help.acdsystems.com/en/acdsee-home-29/acdsee29.pdf), [viewer commands](https://help.acdsystems.com/en/acdsee-home-29/Content/1Topics/Shortcuts/Viewer_keyboard_shortcuts.htm)

## 7. Candidate register: value and development tradeoffs

**Priority A**: common, high-value everyday functionality. **Priority B**: worthwhile next-stage organization. **Priority C**: useful for particular libraries or requires a feasibility study. **Defer/exclude**: insufficient value now or outside agreed scope. These labels do not assign a release. “Partial” means related behavior already exists and only the stated extension is proposed.

## 8. Recommended release sequence

**0.1.43 should concentrate on the three confirmed items and a coherent browsing experience.** The candidates are a product backlog, not a realistic single-release promise.

1. **R43-01 and R43-02 first:** clear date provenance and main-gallery search, with visible state, correct counts, whole-catalog matching, and predictable paging.
2. **R43-03 as its own validated workstream:** automatic naming with trusted references, uncertainty, correction, and provenance. Do not delay useful gallery search while recognition quality is being evaluated. If quality evidence is insufficient, leave automatic naming open and report it honestly rather than treating the current suggestion threshold as approval.
3. **The smallest high-value browsing additions:** C09 previous/next plus return-to-position; C01 photo/video and date-range filters using already available metadata. These are recommended additions to the plan, not accepted scope yet.
4. **Next organization slice:** C08 general gallery selection, C04 favorites, C02 manual albums, C06 captions, C12 source/import browsing, and C10 calendar navigation. Selection is a shared foundation; grouping those changes reduces duplicated UI and recovery work.
5. **Then richer organization:** C03 saved rules, C07 tag vocabulary management, C13/C14 date/metadata improvements, C15/C16 person management, and C27 selected-original export. A basic People-to-gallery entry can be brought forward with R43-02 when inexpensive; richer person records should be planned explicitly.
6. **After that, evaluate AI/scale additions:** C22 visual duplicates, C24 OCR, C25 semantic content search, C26 video discovery, and C29 standard sidecars. Choose by the actual library's needs; model/provider feasibility is a separate gate.

The most compelling new feature beyond the three confirmed changes is **manual albums supported by gallery selection**. The best small convenience is **favorites**. The strongest immediate usability repair is **viewer next/previous and return-to-results**. The highest-potential later retrieval feature is **local OCR or semantic search**, depending on whether documents or remembered scenes dominate the library.

Existing security, installer, backup, and final target-validation obligations remain tracked separately. This research does not close them, reclassify them, authorize deferred investigations, or change original-preservation rules.

## 9. Acceptance rules that prevent another missing-basics cycle

For each feature, specify an ordinary user journey before implementation. A short common checklist should apply to every browsing and organization change:

- **Find:** search the eligible catalog, not just visible thumbnails; distinguish exact person/tag filters from general text; make approximate AI matches apparent.
- **Browse:** keep the query/filter, count, sort, page or scroll position, and viewer sequence consistent. Returning from an item should restore context. Explain index-not-ready and no-results states differently.
- **Organize:** allow one or many items; show the exact operation scope; avoid turning album removal, tag removal, unstacking, archive, or reject into file deletion.
- **Correct:** user changes take precedence; preserve original and corrected values where relevant; provide appropriate undo and explicit merge conflict handling.
- **Recover:** new metadata, ordering, rules, identities, and relationships must survive restart, backup/restore, export, and upgrade/rollback. New fields are not complete merely because the grid displays them.
- **Scale:** preserve bounded paging/jobs, stable ordering, progress/cancel behavior, and recovery after partial failure. Do not load the whole media library into the browser to implement filters.
- **Access:** keyboard controls, clear focus, labels, and narrow layouts are part of the same flow; management controls must not overwhelm ordinary viewing.
- **Preserve:** operations change catalog metadata or derived copies; original bytes and external sources remain authoritative and untouched.

Suggested end-to-end release scenario: import a mixed batch; find Alice in the main gallery; narrow to a date range; open a result and move to the next; return to the same results; select several items; apply an available organization action; restart; export the selection; and restore organization from backup. Exercise only the actions actually included in that release, and include ambiguous names, multi-person photos, missing dates, hidden items, failed analysis, and duplicates.

## 10. Planning decisions and research limits

The review supports identifying these functions as expected candidates earlier in product planning. It does not imply that every large commercial feature belongs in a local prototype. A useful standing capability checklist is: **import, preserve, browse, find, group, select, annotate, correct, export, recover**. The current imbalance is mainly in browse/find/group/select/annotate.

No packages were installed, no application behavior was changed, and no release was built or published for this report. The confirmed backlog and planning references were updated locally. The new candidate priorities remain recommendations for subsequent release scoping.

This inventory covers the organization/access functionality found in the reviewed manuals, including lower-value and out-of-scope categories. It is not a claim to exhaust every feature, edition, historical plugin, or undocumented behavior of seven products. Before implementing a candidate, confirm its exact user journey and the chosen dependency's current Windows compatibility, license, resource behavior, and restore semantics.
